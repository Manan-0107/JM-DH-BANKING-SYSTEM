Data Control Language — Manage access and permissions
GRANT
-- Grant SELECT on Customer table to a user
GRANT SELECT ON banking_db.Customer TO 'banker_user'@'localhost';

-- Grant INSERT, UPDATE on Account to a user
GRANT INSERT, UPDATE ON banking_db.Account TO 'branch_mgr'@'localhost';

-- Grant all privileges on Branch
GRANT ALL PRIVILEGES ON banking_db.Branch TO 'admin_user'@'localhost';

Gives specific privileges to users on database tables.

REVOKE
-- Revoke INSERT on Account from a user
REVOKE INSERT ON banking_db.Account FROM 'banker_user'@'localhost';

-- Revoke all privileges on Loan from a user
REVOKE ALL PRIVILEGES ON banking_db.Loan FROM 'temp_user'@'localhost';

Removes previously granted privileges from users.

Transaction Control Language — Ensure data consistency
COMMIT
START TRANSACTION;

UPDATE Account SET account_balance = account_balance - 5000
WHERE account_id = 101;

UPDATE Account SET account_balance = account_balance + 5000
WHERE account_id = 102;

COMMIT;  -- Both updates are permanently saved

Permanently saves all changes made during the current transaction.

SAVEPOINT
START TRANSACTION;

INSERT INTO Transaction (transaction_id, account_id, customer_id, amount)
VALUES (301, 101, 1, 5000);

SAVEPOINT after_insert;

UPDATE Account SET account_balance = account_balance - 5000
WHERE account_id = 101;

-- If something goes wrong:
ROLLBACK TO SAVEPOINT after_insert;
-- Only the UPDATE is rolled back, INSERT remains

Creates a checkpoint within a transaction to allow partial rollbacks.

ROLLBACK
START TRANSACTION;

DELETE FROM Loan_Payment WHERE loan_id = 501;
DELETE FROM Loan WHERE loan_id = 501;

-- Oops! Wrong loan. Undo everything:
ROLLBACK;  -- Both DELETEs are undone

Undoes all changes made during the current transaction (or back to a savepoint).

Project Documentation

From ER model to 3NF — the complete DBMS journey.

Banking Database Management System

This project implements a comprehensive banking database system that manages branches, bankers, customer accounts, loans, transactions, and credit cards. The system is designed to handle real-world banking operations with proper referential integrity, normalization up to 3NF, and full SQL coverage including DDL, DML, DQL, DCL, and TCL operations.

Use Cases
  • Manage branch-wise banking operations and banker assignments
  • Handle customer accounts with multiple account types
  • Process loans with payment tracking through Loan Payment records
  • Link borrowers to loans and customers via the Borrower bridge table
  • Record transactions between accounts and customers
  • Issue and manage credit cards tied to accounts and customers
Entities

The database consists of 9 entities: Branch, Banker, Account, Customer, Loan, Loan Payment, Borrower, Transaction, and Credit Card.

Normalization to 3NF

Functional Dependencies
Branch: branch_id → branch_name, branch_address, assets
Banker: banker_id → banker_name, branch_id
Account: account_id → account_balance, account_type, branch_id
Customer: customer_id → customer_name, dob, mobileno, account_id
Loan: loan_id → issued_amount, remaining_amount, branch_id, account_id
Loan Payment: loan_payment_id → loan_id, amount
Borrower: borrower_id → loan_id, customer_id
Transaction: transaction_id → account_id, customer_id, amount
Credit Card: credit_card_id → expiry_date, card_limit, account_id, customer_id
1NF Analysis

All tables have atomic values in each column, a defined primary key, and no repeating groups. ✅ All relations are in 1NF.

2NF Analysis

All non-key attributes are fully functionally dependent on the entire primary key (each table has a single-column PK). There are no partial dependencies. ✅ All relations are in 2NF.

3NF Analysis

No transitive dependencies exist — every non-key attribute depends directly on the primary key and not on any other non-key attribute. For example, in Customer, mobileno depends on customer_id, not on customer_name. ✅ All relations are in 3NF.

Final Decomposed Relations

The schema requires no further decomposition. All 9 tables are already in 3NF with their original attributes preserved.

Integrity Constraints

PRIMARY KEY

Every table has a unique primary key: branch_id, banker_id, account_id, customer_id, loan_id, loan_payment_id, borrower_id, transaction_id, credit_card_id

FOREIGN KEY (Referential Integrity)
  • Banker.branch_id → Branch.branch_id
  • Account.branch_id → Branch.branch_id
  • Customer.account_id → Account.account_id
  • Loan.branch_id → Branch.branch_id
  • Loan.account_id → Account.account_id
  • Loan_Payment.loan_id → Loan.loan_id
  • Borrower.loan_id → Loan.loan_id
  • Borrower.customer_id → Customer.customer_id
  • Transaction.account_id → Account.account_id
  • Transaction.customer_id → Customer.customer_id
  • Credit_Card.account_id → Account.account_id
  • Credit_Card.customer_id → Customer.customer_id
NOT NULL

branch_name, branch_address, banker_name, customer_name, account_type, mobileno, issued_amount, remaining_amount, expiry_date, card_limit

UNIQUE

mobileno (Customer), credit_card_id (Credit Card)

CHECK
  • assets >= 0 (Branch)
  • account_balance >= 0 (Account)
  • issued_amount > 0 (Loan)
  • remaining_amount >= 0 (Loan)
  • amount > 0 (Transaction, Loan Payment)
  • card_limit > 0 (Credit Card)
  • account_type IN ('Savings', 'Current', 'Fixed Deposit')

Views, Procedures, Functions & Triggers

View
CREATE VIEW customer_account_view AS
SELECT c.customer_id, c.customer_name, c.mobileno,
       a.account_id, a.account_type, a.account_balance,
       b.branch_name
FROM Customer c
JOIN Account a ON c.account_id = a.account_id
JOIN Branch b ON a.branch_id = b.branch_id;

-- Query the view
SELECT * FROM customer_account_view
WHERE account_type = 'Savings';
Materialized View (Simulated in MySQL)
-- MySQL does not support MATERIALIZED VIEW directly.
-- Simulated using a summary table + scheduled refresh:

CREATE TABLE branch_summary_mv AS
SELECT b.branch_id, b.branch_name,
       COUNT(a.account_id) AS total_accounts,
       SUM(a.account_balance) AS total_deposits
FROM Branch b
LEFT JOIN Account a ON b.branch_id = a.branch_id
GROUP BY b.branch_id, b.branch_name;

-- To refresh: TRUNCATE and re-INSERT
TRUNCATE TABLE branch_summary_mv;
INSERT INTO branch_summary_mv
SELECT b.branch_id, b.branch_name,
       COUNT(a.account_id), SUM(a.account_balance)
FROM Branch b
LEFT JOIN Account a ON b.branch_id = a.branch_id
GROUP BY b.branch_id, b.branch_name;
Stored Procedure
DELIMITER //
CREATE PROCEDURE TransferFunds(
  IN from_acc INT, IN to_acc INT, IN transfer_amt DECIMAL(15,2)
)
BEGIN
  DECLARE from_bal DECIMAL(15,2);
  SELECT account_balance INTO from_bal FROM Account WHERE account_id = from_acc;
  IF from_bal >= transfer_amt THEN
    UPDATE Account SET account_balance = account_balance - transfer_amt WHERE account_id = from_acc;
    UPDATE Account SET account_balance = account_balance + transfer_amt WHERE account_id = to_acc;
    INSERT INTO Transaction (account_id, customer_id, amount)
    VALUES (from_acc, (SELECT customer_id FROM Customer WHERE account_id = from_acc LIMIT 1), transfer_amt);
  END IF;
END //
DELIMITER ;
Function
DELIMITER //
CREATE FUNCTION GetLoanBalance(p_loan_id INT)
RETURNS DECIMAL(15,2) DETERMINISTIC
BEGIN
  DECLARE bal DECIMAL(15,2);
  SELECT remaining_amount INTO bal FROM Loan WHERE loan_id = p_loan_id;
  RETURN bal;
END //
DELIMITER ;
Trigger
DELIMITER //
CREATE TRIGGER after_loan_payment
AFTER INSERT ON Loan_Payment
FOR EACH ROW
BEGIN
  UPDATE Loan
  SET remaining_amount = remaining_amount - NEW.amount
  WHERE loan_id = NEW.loan_id;
END //
DELIMITER ;
